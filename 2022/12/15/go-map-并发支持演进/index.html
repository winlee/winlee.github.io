1. Map 是什么

Go 内建 map 是按键索引的无序集合。每个键对应至多一个值：

Map 是引用语义的数据结构。赋值会复制 map 值所持有的引用，而非复制所有键值对：

因此，多个变量可能指向同一份底层 map；并发访问是否安全取决于所有访问是否正确同步。

2. 键类型、nil 与零值

Map 的键必须是可比较类型，因为运行时需要对键进行相等比较。常见可用类型包括布尔、数值、字符串、指针、Channel、接口，以及字段或元素都可比较的数组和结构体。slice、map 和函数类型不能作为键。

接口类型作为键时，接口的动态值也必须可比较；如果动态值是 slice 等不可比较类型，执行相关 map 操作会在运行时 panic。NaN 是可比较浮点值，但它不等于自身，这种键的查找和删除行为不适合用普通相等直觉推断，设计键时最好避开。

未初始化 map 的零值是 nil：

nil map 可以安全读取、取长度、删除元素，但不能写入。make(map[K]V) 创建可写的空 map；可选容量参数只是初始容量提示，不是最大容量，也不要求运行时精确按该值分配。

3. 更新值与遍历语义

Map 元素不是可取地址的变量，不能写 &m[key]。若 map 的值是结构体，读取 m[key] 得到的是值副本；修改副本不会更新 map：

也可以把值类型设计为指针，但这会改变所有权、共享和内存回收特征，应结合领域模型选择。

Map 遍历顺序没有规范保证，不同遍历之间也不保证一致。不要依赖它做排序或稳定序列化；需要稳定输出时，先收集键，再显式排序。

遍历期间删除尚未访问的键时，该键不会再产生；遍历期间新增的键可能会被访问，也可能被跳过。具体选择不保证固定。即便某个实现通过随机化使顺序看起来经常改变，也不能把这种实现策略当作语言层面的承诺。

4. 并发读写为什么需要同步

普通 map 不支持无同步的并发写，也不支持一个 goroutine 写、另一个 goroutine 同时读。并发读也只有在没有并发写入或其他修改时才可安全进行。未同步读写属于数据竞争，运行时可能报告 concurrent map read and map write 或 concurrent map writes，但不能把这条诊断当成安全机制：有些竞态不会按预期触发该错误，程序仍然是错误的。

4.1 Mutex：最常见、最明确

RWMutex 允许多个读者并行，但写者仍需独占；在读写混合或临界区很短时，它未必比 Mutex 更快。应先使用简单、正确的锁保护，再通过基准测试决定是否需要优化。锁必须保护完整的复合操作，例如“读取、判断、更新”不能只锁其中一个步骤。

4.2 分片锁：提高不同键之间的并行度

若单个锁确实形成热点，可以把键按稳定哈希分配到多个 map 分片，每个分片配一把锁。不同分片上的操作就有机会并行。但分片带来额外复杂度：遍历或快照要按一致的加锁顺序获取多把锁，哈希函数和分片数也会影响负载均衡。分片不是默认方案，需要有性能数据支持。

4.3 sync.Map：专用并发 Map

Go 1.9 引入 sync.Map，它提供并发安全的 Load、Store、Delete 等操作。它使用 any 类型的键和值，读写时需要做类型断言或封装。标准库文档特别推荐的模式包括：

  1. 某个键写入一次，之后读取很多次，例如只增长的缓存；
  2. 多个 goroutine 操作互不重叠的一组键。

一般应用若需要强类型约束、复合不变量或统一遍历快照，map[K]V 加 Mutex 往往更清晰。sync.Map 的安全性也只覆盖它本身的操作，不会自动保护存进 value 的可变对象。

不要把 Load、业务判断、Store 三个独立操作误认为一个原子事务；需要复合原子性时应使用 LoadOrStore、CompareAndSwap 等合适方法，或采用互斥锁保护业务状态。

5. Map 实现的历史演进

语言规范定义了 Map 的行为，但不规定哈希表的具体内存布局。理解历史实现可以解释不少性能文章中的术语，不过不能将这些细节推广为长期兼容承诺。

5.1 传统 bucket 实现

长期以来，Go 的内建 map 使用桶（bucket）组织数据。旧实现的 hmap 保存元素数量、桶数量的对数、哈希种子、当前桶数组、扩容中的旧桶数组和迁移进度等信息。一个 bucket 通常可容纳 8 个键值对，并保存哈希高位信息；冲突过多时通过 overflow bucket 延伸。扩容时，旧数据会逐步搬迁到新桶，而不一定一次性完成全部迁移。

这种设计在 Go 1.23 及之前的默认实现中广为人知。Go 1.24 引入新的 Swiss Table 风格实现后，旧实现仍保留为实验切换选项（GOEXPERIMENT=noswissmap），可用于理解历史行为或进行对照测试，但不应再笼统称为当前默认布局。

5.2 Go 1.24：Swiss Table 风格的内建 map

Go 1.24 的发布说明宣布内建 map 改为基于 Swiss Tables 的实现，目标之一是降低运行时开销。Go 1.25.12 的 internal/runtime/maps 源码说明了其主要结构：

  • 一个 group 有 8 个键值槽位，并配有一个 control word；
  • control word 的每个字节表示槽位状态，已占用时还保存哈希的 7 位摘要（H2）；
  • 哈希的 H1 部分用于选择初始 group，再按探测序列继续查找；
  • 通过对 control word 做位操作，可并行筛查一组槽位的 H2，再对候选键做完整比较；
  • map 由一个或多个 table 组成，借助目录与 extendible hashing 将哈希空间分配到 table，并允许局部 table 扩容或拆分。

重要的是，算法和布局变化并没有改变 Go 程序的 Map 使用契约：键仍需可比较，遍历顺序仍未指定，普通 map 仍需外部同步。不要根据“新实现更快”就推断所有工作负载都一定加速；性能需在真实数据分布、键和值类型、读写比例以及目标 Go 版本上测量。

6. sync.Map 的实现也在演进

sync.Map 与内建 map 是两件不同的事：内建 map 是语言类型；sync.Map 是标准库提供的并发安全容器。Go 1.9 的 sync.Map 文档介绍了并发 map 类型。传统实现采用只读部分与 dirty map 等结构，让部分读取路径可以无锁执行，并在需要时通过锁和 miss 计数完成状态迁移。

Go 1.24 改进了 sync.Map 的实现，发布说明提到对修改操作，尤其是大型 map 中修改不相交键，以及低竞争读取的启动阶段进行了优化。Go 1.25.12 源码中，sync.Map 仍默认使用 read/dirty 结构；另一个基于 Hash Trie 的实现位于实验 build tag goexperiment.synchashtriemap 下。因此，讲“并发支持演进”时应区分标准 API 契约、正式版本默认实现和实验性实现，不能把实验代码误写成默认行为。

无论具体内部实现如何变化，sync.Map 都不能使普通 map 自动线程安全，也不意味着所有并发 map 都应该换成 sync.Map。类型安全、操作组合和基准测试仍是选择依据。

7. 如何选择

需求 常见选择 需要留意
单 goroutine 管理状态 普通 map[K]V 简洁直接
多 goroutine 读写同一集合 普通 map + Mutex 或 RWMutex 锁覆盖所有相关复合操作
键空间热点明显、锁已测得成为瓶颈 分片 map + 多把锁 快照、遍历、跨分片操作更复杂
写入一次、读取很多次，或键集合分散 sync.Map any 类型；复合操作不自动原子化
高度定制的并发索引结构 评估专用库或自定义结构 先明确语义与基准，不要重造并发原语

8. 小结

Go 的 Map 使用体验很轻量，但并发安全不是内建 Map 自动提供的性质。普通 map 的共享访问要么由所有者 goroutine 串行化，要么由锁等同步机制保护；sync.Map 是面向特定访问模式的替代容器。内建 map 从传统 bucket 结构演进到 Go 1.24 的 Swiss Table 风格实现，反映的是运行时实现持续优化，而不是语言层面的行为改变。

记住两条边界：先按规范写正确，再按目标版本测性能；并发容器的实现变化，不等于应用可以省略同步设计。
