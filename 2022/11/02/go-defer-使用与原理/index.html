Go 的 defer 使用与原理
2022 十一月 2日
Go
defer

defer 用于登记一个延迟调用：当前函数即将返回时执行它。它常用于释放资源、解锁和处理清理逻辑。理解调用时机、执行顺序和参数求值规则，可以避免很多隐蔽问题。

1. defer 的介绍

defer 后面必须是函数或方法调用。执行到 defer 语句时，Go 会立即求值被调用的函数以及参数，但不会立即调用它；被登记的调用会在外层函数返回前执行。

func example() {
    defer fmt.Println("cleanup")
    fmt.Println("work")
}

输出：

work
cleanup

同一函数登记多个 defer 时，按后进先出（LIFO）顺序执行：

func example() {
    defer fmt.Println("first")
    defer fmt.Println("second")
    // 返回时依次输出 second、first
}

2. defer 的使用

释放资源

资源获取成功后尽早登记释放逻辑，能让清理代码靠近资源创建的位置：

func readFile(path string) error {
    f, err := os.Open(path)
    if err != nil {
        return err
    }
    defer f.Close()

    _, err = io.Copy(os.Stdout, f)
    return err
}

常见场景包括关闭文件、响应体、数据库连接或事务，以及解锁：

mu.Lock()
defer mu.Unlock()

执行函数退出逻辑

可以用 defer 记录耗时、归还临时状态或执行统一清理。若需要访问函数最终返回值，可以使用命名返回值：

func answer() (result int) {
    defer func() {
        result++
    }()
    return 41
}

return 41 先把 41 赋给 result，然后执行 deferred 函数，因此最终返回 42。

处理 panic

发生 panic 时，Go 会沿当前 goroutine 的调用栈展开，并执行沿途已登记的 defer。recover 通常放在 deferred 函数中，用来捕获当前 goroutine 的 panic：

func protect() {
    defer func() {
        if v := recover(); v != nil {
            log.Printf("recovered: %v", v)
        }
    }()

    doWork()
}

recover 只能在正在展开 panic 的同一 goroutine 中，由 deferred 函数直接调用时生效；它不能捕获其他 goroutine 的 panic。

3. defer 的原理：从编译器到运行时

下面以 **Go 1.25.12（linux/amd64 的通用实现思路）**为例分析源码。编译器策略会随版本、目标架构、函数结构和编译选项变化；_defer 等均是运行时内部实现，不属于 Go 语言规范。

先看一条完整路径：

defer 语句
   │
   ├─ 编译器：求值函数/接收者/参数，决定 defer 实现策略
   │
   ├─ open-coded：保存到当前栈帧的槽位，并置位 deferBits
   │
   └─ linked defer：构造 _defer 记录，挂入当前 goroutine 的 defer 链
          │
          ├─ 正常返回：执行返回路径上的 defer 处理代码
          └─ panic：gopanic 遍历栈帧，由 nextDefer 找到并执行待处理调用

3.1 编译器先改写 defer 调用

编译器前端把 defer f(x) 表示为 defer 语句节点（内部 IR 中为 ODEFER）。在 cmd/compile/internal/walk/stmt.go 中，编译器标记函数含有 defer，并统计静态 defer 数量；之后 SSA 阶段选择生成 open-coded 代码还是运行时调用。

无论采用哪条路径，调用所需的数据都必须在执行 defer 语句时确定：函数值、方法接收者和实参在登记点求值。编译器把它们保存到之后可供延迟调用使用的位置；如果是闭包，保存的是闭包值及其捕获环境。

func example() {
    n := 1
    defer fmt.Println(n) // 保存的实参是 1
    n = 2
}

这里保存的是整数 1，而不是 n 这个变量的位置。闭包则不同：

func example() {
    n := 1
    defer func() { fmt.Println(n) }() // 闭包捕获 n
    n = 2
}

闭包执行时读取捕获的变量，因此输出 2。这是“实参立即求值”和“闭包延迟执行”共同造成的，不是 defer 参数求值规则的例外。

3.2 当前编译器的三种实现路径

Go 1.25.12 编译器源码会把 defer 区分为 open-coded、stack-allocated、heap-allocated。这是编译器实现策略，不应理解成语言层面对每条 defer 的固定承诺。

路径 A：open-coded defer

这是很多简单函数的优化路径：编译器不必为每个 defer 都调用运行时注册函数，而是将必要状态直接放进当前函数的栈帧，并在函数退出路径生成调用代码。

编译器为这些 defer 维护一个字节大小的 deferBits 位图，并为每个静态 defer 调用保存函数值和参数的槽位。执行到某条 defer 时，大致完成两件事：

  1. 把已求值的函数值、接收者和实参保存到该调用对应的槽位；
  2. 把该 defer 对应的 bit 置为 1，表示它已经执行过、需要在退出时调用。

退出时，生成的代码检查位图，从高位到低位找到最后登记的待执行 defer，取出对应函数和参数调用，并清除该 bit。由于 defer 按 LIFO 语义执行，位编号和遍历方向会被编译器安排成逆登记顺序。

如果某个 defer 位于条件分支中，分支未执行时 bit 不会置位，因此返回时跳过；同一条静态 defer 语句若处在循环中，则可能执行任意多次，单个位图无法表达多次登记，通常需要走链表式路径。

当前源码中可见的常见限制包括：静态 defer 点不超过 8 个、defer 不处于循环，以及函数退出路径数量和其他目标条件合适。具体条件以所用 Go 版本的编译器为准。编译器还将 defer 位图和槽位偏移写入 FUNCDATA_OpenCodedDeferInfo，供 panic 栈展开时定位仍未执行的 defer。

路径 B：stack-allocated defer

当不能使用 open-coded，但编译器能证明 defer 记录不会逃逸时，可把 _defer 记录直接放在当前函数栈帧中。生成代码初始化记录，再调用 runtime.deferprocStack 将它挂入链表。

这种路径避免为 defer 记录单独进行堆分配，但它仍然是运行时链表管理，不等同于 open-coded。运行时必须记录该记录所属栈帧；goroutine 栈可能增长或复制，记录中的栈指针也必须按照运行时规则处理。

路径 C：heap-allocated defer

若 defer 记录不能安全放在栈上，编译器会生成调用 runtime.deferproc 的代码。运行时通过 newdefer 获取记录：优先使用 P 级 defer pool（必要时从调度器池补充），没有可复用记录时再分配 _defer；随后把记录挂到 gp._defer 链表头。

Go 1.25.12 的 runtime._defer 关键字段包括：

字段 作用
fn 延迟调用的函数值；open-coded defer 不一定有单独记录，因此允许为 nil
link 指向同一 goroutine defer 链中的下一条记录
sp、pc 记录 defer 所属栈帧的位置，用于匹配正在展开的帧
heap 标记记录来自堆/运行时池，还是由编译器放在栈上

这条路径的登记逻辑可以概括为：

d := newdefer()
d.link = gp._defer
gp._defer = d
d.fn = fn
d.pc = callerPC
d.sp = callerSP

这是对 runtime.deferproc 的删减示意，不是可直接使用的代码。实际源码还处理系统栈约束、栈指针有效性、pool、GC 与并发安全等细节。

3.3 正常返回：返回值先确定，再运行 defer

对常规返回，编译器会生成相应的退出路径。open-coded defer 由该函数生成的代码直接检查位图并调用；链表式 defer 则由编译器安排的 runtime.deferreturn 处理。

runtime.deferreturn 创建运行时的 defer 执行上下文，反复调用 nextDefer 取出当前函数帧的下一条 defer 并执行。链表记录弹出后，运行时清除函数引用，避免延长闭包或其捕获对象的存活时间；堆记录之后可回收到 defer pool。

对于命名返回值，编译器把 return expr 展开成“先写返回变量，再运行退出逻辑，最后返回”。例如：

func f() (n int) {
    defer func() { n++ }()
    return 10
}

10 先赋给 n，defer 再把 n 改为 11，最终返回 11。未命名返回值的返回表达式也会先计算到返回位置；但 defer 中修改某个局部变量不会反过来改写已经计算好的返回值。

3.4 panic 展开：运行时沿栈帧找 defer

panic 进入 runtime.gopanic 后，运行时创建 _panic 状态并循环调用 nextDefer。每次拿到一个延迟函数就执行它：

  1. 如果当前栈帧有未执行的 open-coded defer，运行时读取编译器写入的 FUNCDATA_OpenCodedDeferInfo，检查 deferBits，按逆序取出槽位中的调用，并先清除对应 bit；
  2. 否则检查 gp._defer 链表头的 sp 是否属于当前栈帧。匹配时弹出记录并返回其 fn；
  3. 当前帧没有待执行 defer 时，继续用栈展开器寻找外层帧，直到找不到更多 defer。

因此运行时需要同时理解 open-coded 元数据和链表记录：它们是两种存储形式，但最终都由 panic 展开流程按语言要求调用。defer 内再次 panic 时会进入新的 panic 展开；recover 能否生效则由运行时检查当前执行位置是否是正在处理的 panic 中最顶层 deferred 调用（源码通过参数区地址等信息校验）。

3.5 如何在本机观察编译器选择

对当前 Go 编译器，可以用调试开关查看 defer 分类：

go build -gcflags='-d=defer=2' ./...

输出会提示某条 defer 是 open-coded、stack-allocated 还是 heap-allocated。也可以查看汇编：

go build -gcflags='-S' -o app .

在汇编中搜索 deferproc、deferprocStack 或 deferreturn 可以发现链表路径；找不到这些调用并不表示没有 defer，可能是 defer 已被 open-code 到函数退出路径。

阅读结论： defer 的语言语义由规范保证；“位图”“_defer 链表”“栈分配/堆分配”和相关运行时函数名都是特定编译器与运行时版本的实现细节。性能分析或源码学习时应锁定 Go 版本，业务代码则不要依赖这些内部布局。

4. defer 的注意事项

参数在登记时求值

func example() {
    n := 1
    defer fmt.Println(n)
    n = 2
}

这里会打印 1。如果想在退出时读取最新值，使用闭包。

循环中的 defer 会等函数返回

func process(paths []string) error {
    for _, path := range paths {
        f, err := os.Open(path)
        if err != nil {
            return err
        }
        defer f.Close() // 所有文件会在 process 返回时才关闭
        _ = f
    }
    return nil
}

大量迭代时，这会让资源一直占用到整个函数结束。可以把每次迭代的工作放进单独函数，让该函数返回时及时执行 Close；或者在循环中显式处理关闭。

deferred 调用的返回值会被丢弃

例如 defer f.Close() 不会自动把 Close 的错误合并到外层函数的返回错误中。如果关闭错误也必须报告，应使用闭包并明确更新命名返回值，或显式检查错误。

多个 defer 的顺序是反向的

defer unlock()
defer closeFile()

退出时先执行 closeFile()，再执行 unlock()。登记顺序应与期望的清理顺序相匹配。

defer 不会自动捕获所有 panic

只有符合调用条件的 recover 才能停止当前 goroutine 的 panic 展开。不要把它当作跨 goroutine 的异常处理机制，也不要在没有明确恢复策略时吞掉 panic。

热路径中避免无依据地优化

defer 语义清晰，适合常规资源清理。若它位于极高频的性能热点，应先通过基准测试和性能分析确认开销，再决定是否改写；不要仅凭旧版本的性能结论一概避免使用。
